## 1. Headline finding

The repository publishes a three-specification release (Baseline / Slack-Plus / Core) for the
five monthly releases 2026-03 through 2026-07, is set up to continue publishing three
specifications monthly, and advertises the Core specification through manifests, WordPress
plugins, the public dashboard, and remote iFastNet paths. Direct diff of every 2026-03..07
Core artifact against its Baseline sibling shows that Core has never been an actual companion
specification: every numeric field is byte-identical to Baseline. `build_core_weights` is
defined in `scripts/compute_dmi_release.py` but is never called anywhere in the codebase. The
Core spec parameters block (`"inflation_measure": "CORE_CPI"`,
`"excluded_categories": ["CPI_FOOD_BEVERAGES"]`) declares category exclusion and a core-CPI
inflation series, but the numeric payload in the same file is Baseline. The metadata is
therefore false metadata, in the sense that it does not describe the computation that
produced the numbers in the same file. This audit makes no claim about how or why that
happened; that determination is part of the Phase 2 provenance work.

This is the central alignment failure between the concept note (v0.4.6, "Core is intended
but not implemented") and the repository. All other v0.1.12 defects listed in this audit are
either downstream of this failure or independent issues that would remain even if Core were
withdrawn today.

## 2. Evidence — Core artifacts are Baseline clones

**Method.** For each period 2026-03 through 2026-07 I loaded
`data/outputs/dmi_release_<PERIOD>.json` (Baseline) and
`data/outputs/dmi_release_<PERIOD>_core.json` (Core) and compared:

- The full root key set on each file. Observed root keys (v0.1.12 release JSON shape):
  `reference_period`, `parameters`, `dmi_by_group`, `summary_metrics`,
  `inflation_contributions`, `metadata`, `specification`, `description`.
- `dmi_by_group[i]` for every quintile. Observed row keys: `group_id`, `dmi`, `inflation`,
  `slack`. (There is **no `slack_u3` field** in current release output. The previous audit
  revision claimed `slack_u3` based on `dmi_output.schema.json`; the schema is stale and does
  not match the actual current output — see §4.2.)
- `summary_metrics` — a **single object** on the root, not an array. Its keys are the
  v0.1.12 canonical metrics: `dmi_median`, `dmi_stress`, `income_pressure_spread`,
  `most_pressured_group`, `least_pressured_group`, `income_pressure_tilt`. There is **no
  `dmi_dispersion_q5_q1` field** in current release output.
- `inflation_contributions[*].contribution` for every category × quintile.
- The `parameters` object on the root.

**Result.** For every period 2026-03 through 2026-07:

- Every quintile's `dmi`, `inflation`, and `slack` value in the Core file is bytewise equal
  to the same field in the Baseline file (Python `==` on the parsed floats).
- Every `summary_metrics` field is bytewise equal.
- Every `inflation_contributions.contribution` value is bytewise equal.
- The `parameters` block differs only in two labels: Core has
  `inflation_measure: "CORE_CPI"` and `excluded_categories: ["CPI_FOOD_BEVERAGES"]`, while
  Baseline has `inflation_measure: "HEADLINE_CPI"` and no `excluded_categories`.

Representative example — 2026-07 (from `data/outputs/dmi_release_2026-07.json` and
`data/outputs/dmi_release_2026-07_core.json`):

```
Baseline: dmi_median=7.516957462855907  dmi_stress=7.552376716747651  Q1.slack=4.1
Core    : dmi_median=7.516957462855907  dmi_stress=7.552376716747651  Q1.slack=4.1   (identical)
Slack+  : dmi_median=11.316957462855907 dmi_stress=11.352376716747651 Q1.slack=7.9   (baseline + 3.8 shift)
```

Slack-Plus differs from Baseline by (U-6 − U-3) = (7.9 − 4.1) = 3.8, applied uniformly to
every quintile's DMI, as the concept note describes. Core does not differ from Baseline at
all.

**Root cause — `scripts/compute_dmi_release.py`:**

- Defines `build_core_weights(weights_df)` at line 215 that reweights CPI categories after
  removing food & beverages.
- `grep -R "build_core_weights"` finds one hit only: the definition itself. There are no
  callers anywhere in the repository.
- `load_slack_for_spec(spec, ...)` at line 228 branches on `spec` but returns U-3 for both
  `"baseline"` and `"core"`, and U-6 only for `"slack_plus"`.
- Around line 347 the spec branch does:
  ```python
  if spec == "core":
      results["parameters"]["inflation_measure"] = "CORE_CPI"
      results["parameters"]["excluded_categories"] = ["CPI_FOOD_BEVERAGES"]
  else:
      results["parameters"]["inflation_measure"] = "HEADLINE_CPI"
  ```
  The parameters block is *labeled* Core, but the actual weights, inflation series, and
  slack series fed to the DMI computation are identical to Baseline.
- No CPI dataset in the repository has food & beverages removed; no core-CPI-specific
  inflation series is loaded; `build_core_weights` is never applied.

**Provenance note.** The audit establishes that current Core files are Baseline clones with
false metadata; it does not establish *how* they were produced (whether by direct invocation
of `compute_dmi_release --spec core` or by some prior manual generation). The Phase 2
investigation must record that provenance from git history for at least one representative
period before deleting the files, so the withdrawal record is accurate. See Phase 2 work
items.

**Consequence.** Every Core file in `data/outputs/`, every Core row in `specifications.json`,
every Core `spec_urls` entry in `releases.json` and `latest.json`, every Core download link
rendered by `web/wp-plugins/dmi-release-data/dmi_release_data.php`, and every Core reference
in `web/dashboard.html` presents a Baseline computation labeled as "Core (excludes food and
beverages)". This misrepresents the pipeline's capabilities. It is inconsistent with the
concept note's explicit statement that Core is not implemented and not publishable in
v0.1.12.

## 3. Manifests — `data/outputs/`

### 3.1 `data/outputs/specifications.json` — combined mixed-period + mixed-value P0

Verbatim structure (as of audit):

- `schema_version: "0.2.0"`
- `generated_at: "2026-08-10T05:08:42.852531Z"`
- `reference_period: "2026-06"`
- `headline_spec: "baseline"`
- `specifications: [baseline, slack_plus, core]`
- `robustness_assessment.pressure_tilt_sign_consistent: true` (v0.1.12 field name — correct)

**P0 combined defect.** The file combines three inconsistent facts:

1. **Reference period says 2026-06.** `reference_period: "2026-06"`.
2. **Paths and DMI values say 2026-07.** Every `release_json` path in the file points to a
   2026-07 file (`/data/outputs/dmi_release_2026-07.json`,
   `/data/outputs/dmi_release_2026-07_slack_plus.json`,
   `/data/outputs/dmi_release_2026-07_core.json`), and every `metrics.dmi_median` /
   `metrics.dmi_stress` / `metrics.income_pressure_spread` /
   `metrics.income_pressure_tilt` value matches the 2026-07 release payload exactly
   (Baseline `dmi_median = 7.516957462855907`, `dmi_stress = 7.552376716747651`; Slack-Plus
   `dmi_median = 11.316957462855907`).
3. **Baseline `slack` says 4.2, but the actual 2026-07 Baseline release uses 4.1.** In
   `specifications.json`: `specifications[0].metrics.slack = 4.2`. In
   `data/outputs/dmi_release_2026-07.json`: every quintile's `slack = 4.1`, and
   `parameters.slack_measure = "u3"`. The Slack-Plus block in `specifications.json` shows
   `slack = 7.9`, which matches the actual 2026-07 Slack-Plus release. So the Baseline slack
   value in `specifications.json` is not merely stale-with-2026-06, it also does not match
   any known 2026-07 value; it must have come from a different source or a partial
   regeneration.

This is not a simple "regenerate and move on" defect. Phase 2 must determine the production
path that produced `specifications.json` in this state — whether the writer takes Baseline
metrics from a separate cached source, whether a manual edit occurred, or whether a
partial-refresh script wrote paths and DMI values but preserved older slack — and add a
regression test that guards against a repeat. The regression test must cover, at minimum:

- `reference_period` == the `release_id` of the current release entries.
- Every `release_json` path resolves to a file that exists in the working tree.
- Every `metrics` block in the file exactly matches the corresponding raw release JSON
  (`dmi_median`, `dmi_stress`, `income_pressure_spread`, `income_pressure_tilt`,
  `most_pressured_group`, `least_pressured_group`, `slack`, `slack_measure`).

Without this test, a future write path can silently reintroduce the same mixed state.

**Core row.** The Core metrics block in `specifications.json` is byte-identical to the
Baseline block in the same file (same `dmi_median`, `dmi_stress`, `income_pressure_spread`,
`income_pressure_tilt`, `most_pressured_group`, `least_pressured_group`, `slack: 4.2`,
`slack_measure: "u3"`). This is downstream of §2.

### 4.1 `releases.schema.json` (consumed by `releases.json` and `latest.json`)

- Draft 2020-12.
- Root requires `schema_version`, `generated_at`, `current_release_id`, `releases`.
- Each release requires `release_id`, `data_through_label`, `published_at`, `status`,
  `methodology_version`, `summary`, `summary_facts`, `spec_urls`, `metrics`.
- **`spec_urls` requires all three of `baseline`, `slack_plus`, `core`.** A two-spec
  operational manifest (Baseline + Slack-Plus, no Core) fails validation against this
  schema.
- **Each `spec_url_block` requires `csv`, `parquet`, AND `release_note`.** Current
  `releases.json` violates this: `slack_plus` and `core` blocks have only `csv` and
  `parquet`. The current `releases.json` therefore does not validate against its own
  declared schema.
- `metrics` requires the v0.1.12 canonical fields and enforces
  `income_pressure_spread >= 0` (correct).
- `spec_urls` and `metrics` both use `"additionalProperties": false`.

### 4.2 `dmi_output.schema.json` (declared consumer: per-release `dmi_release_<PERIOD>*.json`)

- Every `dmi_by_group` item requires `slack_u3`. Current release output uses `slack` (with
  the measure captured separately in `parameters.slack_measure`). Current output therefore
  **does not validate** against this schema.
- `summary_metrics` is declared as an array of objects, each requiring `geo_id`, `period`,
  `dmi_median`, `dmi_stress`, `dmi_dispersion_q5_q1`. Current output has
  `summary_metrics` as a single object with the canonical v0.1.12 fields
  (`dmi_median`, `dmi_stress`, `income_pressure_spread`, `income_pressure_tilt`,
  `most_pressured_group`, `least_pressured_group`) and no `dmi_dispersion_q5_q1`. Current
  output **does not validate** against this schema on shape or on required-field terms.
- `metadata.qa_status` and `metadata.inflation_geo_policy_version` are required. Current
  output does have these.
- No `parameters` block is defined at the root. Current output does write a `parameters`
  object at the root. The root has `"additionalProperties": false`, so adding `parameters`
  to the actual output means every actual release JSON violates the schema on that basis
  as well.

The schema is stale relative to the code that emits the artifacts. This misalignment
is a P0 defect: a release whose current outputs do not validate against their own declared
schema cannot be described as release-ready.

### 4.5 Schema-version compatibility plan (per controlling user decision)

Per user decision 3 (§11 below), the repaired release-manifest contract is a **breaking
change** and adopts a new major version. Concretely:

- `releases.schema.json` and `latest.json` schema move to `3.0.0`. Under 3.0.0:
  - `spec_urls.required` = `["baseline", "slack_plus"]` (Core not accepted; not merely
    optional).
  - Baseline-owned `release_note` moves out of the per-spec `spec_url_block` and becomes a
    top-level per-release field (`release_note` on the release object). Per-spec URL blocks
    require only `csv` and `parquet`.
  - `metrics` unchanged (already correct for v0.1.12).
  - `schema_version` root value must match `3.0.0`.
- If practical, the historical 2.0.0 schema will be retained as
  `schemas/legacy/releases.schema.v2.0.0.json` for validating archival instances. Phase 4
  will determine whether any historical instance actually validates under 2.0.0 (given the
  `release_note`-in-block requirement, no current instance does).
- `dmi_output.schema.json` is re-derived from actual current output shape rather than
  patched. The new version realigns `slack`, `summary_metrics` (single-object), root
  `parameters` block, and canonical summary metric names. Version bump: also a breaking
  change; a separate breaking-schema version bump is applied to this schema. Historical
  archive strategy same as for `releases.schema.json` if practical.

This is a Phase 2/4 implementation task, not a Phase 1 evidence item; it is recorded here so
the constraints for the implementation are unambiguous before edits begin.
